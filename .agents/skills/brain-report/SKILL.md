# Отчёты по записям хранилища

Из каталога программы выполняй `python3 -m second_brain --vault "$VAULT"` с командами ниже. Для недельного обзора **по снимку закрытого плана** используй [brain-weekly-review](../brain-weekly-review/SKILL.md).

Готовый выпуск можно найти через `report-list --match "часть названия" --limit 5`. Для проверки основания вызови `report-source ID --index N`. Номер основания указан в его `href` и отсчитывается с нуля. При изменении исходной строки сравни сохранённую цитату с текущей записью.

У исторического выпуска поле `releaseDate` в выдаче показывает дату выхода, когда она известна. Границы отчётного периода и время создания карточки читаются отдельно. Серия может содержать архивные выпуски без установленного периода.

## Выбрать типовой формат

Эти шаблоны доступны и в пустом хранилище. Для поиска по названию или адресату используй `report-template-list --match "встреч" --limit 5`. Параметр `--origin custom` выбирает пользовательские шаблоны, `--origin builtin` — коробочные, включая редакции владельца. Прочитай выбранную версию через `report-template-show ID`.

- **Итоги недели по направлению** (`weekly-direction`). Найди направление по названию. При запросе «за прошлую неделю» возьми предыдущую календарную неделю в часовом поясе владельца. Для текущей недели укажи дату, по которую есть сведения. Проверь датированные заметки, события проектов и работы самого направления. Команды `overview --states --direction ID` и `project-updates ID` помогают найти нужные записи. Первый обзор показывает последнее известное состояние. Проверь остальные события недели по источникам, прежде чем делать вывод об охвате. [Как найти записи направления](../brain-overview/SKILL.md)
- **Подготовка к встрече 1:1** (`one-on-one`). Найди собеседника и общие договорённости через `people --match "имя"` и `person ID`. Для первой встречи начни с ожиданий участников. Формулируй вопросы от лица того, кто готовится к разговору. В общий текст включай основания, которые уместно открыть обоим участникам: ссылка покажет соседние строки и даст доступ к файлу. Если владелец явно просит личные заметки для себя, приведи их отдельно в его чате. [Карточка человека и область видимости фактов](../brain-person/SKILL.md)
- **Повестка созвона по теме** (`topic-agenda`). Возьми тему из запроса, найди относящиеся к ней решения и ограничения. Сформулируй, к чему участники хотят прийти. Преврати недостающие сведения в вопросы и расположи их в порядке обсуждения. При отсутствии прошлой встречи можно готовить повестку по тематическим материалам.
- **Итоги встречи** (`meeting-summary`). Начни с протокола или записи состоявшегося разговора. Проверь, на какие предложения участники согласились, кто взял действие и какой срок прозвучал. Пункт повестки сам по себе не подтверждает решения.
- **Записка для принятия решения** (`decision-brief`). Найди рассматриваемые варианты и ограничения в исходных записях. Укажи, по каким критериям сравниваешь варианты. Для уже принятого решения приведи основание выбора.
- **Результаты проверки** (`test-results`). Возьми условия и наблюдения из журнала проверки. Укажи, к какому образцу, периоду или прогону относится вывод. Если критерий успеха был задан заранее, сверь его с фактом.
- **Статус проекта** (`project-status`). Прочитай `show ID --brief` и нужные страницы `project-updates ID`. Для серии сверь изменения с предыдущим выпуском. По связанным работам проверь согласованный срок, прогноз и дату завершения. [Сводка проекта](../brain-record/SKILL.md) · [Как читать даты](../brain-plan/references/schedule.md)
- **Ретроспектива завершённой работы** (`retrospective`). Сопоставь исходное ожидание с зафиксированным результатом. Проверь основания объяснений и сформулируй изменение на будущее. Для согласованного действия укажи запись о договорённости.

## Собрать выпуск

Период событий и дата актуальности сведений могут различаться. Например, воскресенье закрывает отчётную неделю, а в понедельник владелец уточняет результат. При наличии подтверждённой даты среза передай её в `report-save --as-of YYYY-MM-DD`. Время сохранения файла определяется отдельно.

1. Определи адресата, тему, формат и границы периода из запроса или серии. Если ID шаблона неизвестен, найди формат через `report-template-list --limit 10`. Если его нет на странице и вернулся `nextOffset`, продолжи с `--offset`. Для серии вызови `report-series-list`, затем `report-series-show ID`. Проверь предложенные `nextStart` и `nextEnd`. Если задан другой период, проверь, какие выпуски уже есть. Чтобы завести серию или изменить формат, открой [команды серий и шаблонов](references/formats.md).
2. Прочитай конкретную версию через `report-template-show ID --version N`. В ней заданы читатели, правила подачи и структура Markdown. До составления очередного выпуска прочитай предыдущий выпуск **этой серии** через `report-list --series ID` и `report-show ID`. При работе задним числом сравнивай с периодом, предшествующим запрошенному. Для первой встречи или первого выпуска начинай с доступной фактуры.
3. Найди подтверждения по теме в [записях vault](../brain-ask/SKILL.md). Для вопроса про «мою команду» сначала проверь [состав команды](../brain-person/references/teams.md). Проверь нужные строки, даты, единицы и контекст. Учти явно указанные владельцем материалы. Дата редактирования файла сама по себе ничего не говорит о дате события. После пропущенной встречи проверь, охвачены ли изменения с последней состоявшейся. Прошлый выпуск помогает найти открытые вопросы. Подтверждение изменений бери из первоисточников.
4. Подготовь текст для адресата. Сохрани порядок рубрик, лексику, списки и обозначения выбранной версии. Для дайджеста начни с результата и поясни его значение. Для повестки задай решаемый вопрос и оставь достаточно фактов для выбора. Укажи, если вывод применим только к части периода или к отдельному наблюдению. Если данных для обязательной рубрики нет, следуй правилу владельца об этой рубрике и сообщи о пробеле. Не заполняй её вымышленным событием.
5. Подготовь отдельный JSON-массив оснований. Для каждого существенного тезиса сохрани `claim` (какую фразу он подтверждает), `path` относительно vault, `line` с единицы и дословную `quote` с этой строки. Для составного вывода добавь несколько оснований. Если формат требует ссылки в теле, оставь их и там. Текст выпуска хранит только то, что предназначено читателю.
6. Сверь черновик с шаблоном и источниками. Для просьбы о независимой приёмке или сложного выпуска с несколькими источниками используй [редакторскую приёмку](references/review.md). Просьбу показать черновик выполни в чате. Когда владелец просит создать или сохранить выпуск, запиши его после проверки.

```sh
python3 -m second_brain --vault "$VAULT" report-save "$TITLE" \
  --template "$TEMPLATE" --template-version "$VERSION" --template-revision "$REVISION" \
  --body-file "$BODY_FILE" \
  --sources-file "$SOURCES_FILE" --request-id "$REQUEST_ID"
```

Для периодического выпуска добавь `--series ID --start YYYY-MM-DD --end YYYY-MM-DD`. Для разового отчёта за определённый период также укажи обе даты. При повторе той же попытки сохрани прежний ключ запроса. При конфликте найди существующий выпуск и проверь ручные правки. Перечитай сохранённое через `report-show ID`, верни ссылку на Markdown и при необходимости укажи ограничения охвата. Для списка без тел выполни `report-list --limit 5`, продолжай с `--offset` по `nextOffset`.

## Сохранить черновик и утвердить выпуск

Когда владелец просит сохранить черновик для проверки в админке, добавь к `report-save` флаг `--draft`. В серии сохранённый черновик уже занимает свой период. Дай ссылку на него и укажи путь **Отчёты → Выпуски → Статус → Черновики**. После проверки текста и оснований владелец может нажать **Финализировать выпуск**.

Для правки текста существующего выпуска прочитай `report-show ID` и подготовь обновлённый Markdown из поля `body`. Выполни `report-edit ID --revision SHA --body-file "$BODY_FILE"`. Перечитай выпуск и сверь изменённый текст, статус и основания. При конфликте сравни обе версии перед повтором. В админке та же операция доступна в **Отчёты → Выпуски → Редактировать текст**.

По просьбе утвердить существующий черновик найди его через `report-list --status draft --match "часть названия"`, прочитай `report-show ID` и сверь основания. Выполни `report-finalize ID --revision SHA` с ревизией прочитанного файла. Проверь `editorialStatus` в квитанции и верни ссылку на тот же Markdown. При конфликте перечитай выпуск и сверь ручные изменения перед следующей попыткой.
